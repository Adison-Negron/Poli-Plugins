# MPC custom plugin toolchain (Live III, MPC OS 3.10)

How to build, skin and install a native plugin for an Akai MPC Live III on MPC OS 3.10, using the
`open-mpc/mpc-vst-plugins` toolchain. Collected while building Poli-Ess (a de-esser), 2026-11-04.
Facts marked **device** were seen on the Live III; everything else comes from the toolchain's own code and docs.

## 1. Setup

| Item | Where / what |
|---|---|
| Toolchain checkout | `C:\MPC-PLUGINS\mpc-vst-plugins` (`/mnt/c/MPC-PLUGINS/mpc-vst-plugins` in WSL) |
| One folder per plugin | `C:\MPC-PLUGINS\<Plugin>\` holding `build.sh`, `generate_skin.py`, `imgs/`, `src/`, `vst/` |
| Build host | WSL Ubuntu + Docker Desktop (WSL integration on). Every compile and the skin renderer run in containers |
| Target | `"targets": ["aarch64"]` (Gen2). The `.so` comes out in `vst/build/aarch64/` |
| Device install | **No SSH on 3.10.** Use the Plugin Manager USB stick: put the zip in `local-plugins/` on the stick, then in the manager go to the **Local** tab, Install, **APPLY** (MPC restarts) |

Start a new plugin by copying an existing plugin folder, then change these in `vst/vst.json`: `name`, `uid`
(4 characters, unique, never changed after the first release), `so`, and `version`. Then delete `vst/params.lock`
and `vst/build/`.

## 2. Plugin folder layout

```
<Plugin>/
  build.sh               the whole pipeline (section 3)
  generate_skin.py       mockup -> skin images + vst/layout.conf (all coordinates in one place)
  imgs/                  the design: full mockup + a clean background without the controls (same size)
  src/engine.cpp         the mpc_engine() contract (wrapper/engine.h) + your DSP sources
  vst/vst.json           plugin descriptor
  vst/params.json        parameters, in VST index order. Append only: projects store values by position
  vst/params.lock        written on the first build. Commit it: the build fails if a key moves
  vst/layout.conf        generated by generate_skin.py
  vst/skin_post.py       fixes the built skin (knob filmstrip frame counts, section 5)
  vst/skin_assets/       generated PNGs (background, knob strip, toggle images, meter strip)
```

`vst.json` for an effect with a custom skin:
```json
{
  "name": "My-FX", "vendor": "Poli", "uid": "MyFx", "version": 1000,
  "effect": true, "art": "html",
  "so": "my_fx.so", "params": "params.json", "layout": "layout.conf", "skin_post": "skin_post.py",
  "targets": ["aarch64"],
  "defines": {"HAS_DISPLAY_REV": 1, "DISPLAY_REV_NO_UPDATE": 1},
  "build": {"root": "..", "sources": ["src/dsp.cpp", "src/engine.cpp"],
            "cflags": ["-Isrc", "-O3", "-ffast-math", "-U__FAST_MATH__"], "libs": ["-lm", "-lstdc++"]}
}
```
- `"art": "html"` is required for any custom image (`strip=`, `img=`, `art file=`, `meter`).
- `"defines"` is needed only when the engine moves a parameter itself (a meter, a status readout). Section 6.
- `version`: major*1000 + minor*100 + patch*10 (1030 = 1.0.3). **Bump it for every device build.** The Plugin
  Manager offers an update only when the version is higher, and MPC reloads a skin only after a restart, which the
  manager's APPLY does.

## 3. build.sh pipeline

1. **Strip CRLF from the toolchain.** Git on Windows checks `.py` files out with CRLF, and a `#!/usr/bin/env python3\r`
   shebang fails inside Docker with `python3\r: No such file or directory` (exit status 127). Strip only files that
   contain a CR, and end the pipeline with `|| true`. Under `set -euo pipefail`, grep's "no match" otherwise exits
   the script **silently**:
   ```bash
   strip_cr() { grep -rlIU --null $'\r' "$@" 2>/dev/null | xargs -0 -r sed -i 's/\r$//' || true; }
   strip_cr --include='*.py' --include='*.sh' --include='*.awk' --include='*.json' "$MPC_VST/tools"
   ```
   Never `sed -i` files that are already clean: rewriting a file can race an editor or another tool that is saving it.
2. `python3 generate_skin.py` (Pillow; falls back to the `python:3.11-slim` container when WSL has no Pillow).
3. `rm -rf vst/build/skin`, then `"$MPC_VST/tools/build_port.sh" vst/vst.json aarch64`. The first run with `"art": "html"`
   builds the Chromium renderer image, which takes a few minutes.
4. `"$MPC_VST/tools/test_port.sh" vst/vst.json`: x86 host test under ASan/UBSan. It must print `PASSED`.
5. `release.py --so vst/build/aarch64/<so> --skin "vst/build/skin/<Vendor> - VST - <Name>" --entry vst/build/pluginlist-entry.xml --version X.Y.Z --license MIT --id <id> -o dist`.
   Read the version from vst.json so the two never disagree, and delete older zips of this plugin from `dist/` first.
6. `catalog_check.py dist/<zip>` must print `OK`. "manifest has no source_repo" is only a warning.
7. Copy the zip to `<drive>:\local-plugins\` and remove older zips of the same plugin (the manager lists every zip).
   The Poli build.sh files do this through `shared/usb_stick.sh`: `./build.sh E` (or `USB_DRIVE=E`), else they ask at
   the start (Enter = last letter used, kept in `shared/.usb_drive`); `./build.sh none` skips the copy.
   WSL's view of `/mnt/d` goes stale when the stick is plugged in after WSL started, and writes then fail with
   `Permission denied`, so fall back to PowerShell:
   `powershell.exe -NoProfile -Command "Copy-Item -Force -LiteralPath '<wslpath -w zip>' -Destination 'D:\local-plugins\'"`.

**Building several at once: `C:\MPC-PLUGINS\build-all\build.sh`** (2026-11-05). `./build.sh` asks which plugins
(numbers, names or `all`) and the drive, then runs each plugin's own build.sh in turn with that drive and stdin closed
(no prompts after the start), carries on past a failure, logs to `build-all/logs/<time>/`, and prints a summary
(OK / BUILT, NOT COPIED / FAILED, time each). `./build.sh E all` or `./build.sh E Poli-q PoliPlug` asks nothing. It checks
Docker is running before it starts. `./build.sh E copy Poli-q PoliPlug` only copies the zips already built (no build).
The copy turns `/mnt/c/...` into `C:\...` itself (`win_path` in usb_stick.sh): `wslpath -w` said "No such file" for
freshly written zips (2026-11-05), and PowerShell's copy is retried 3 times. **Every new plugin must follow this so build-all picks it up by itself:**
- a `build.sh` in its own folder `C:\MPC-PLUGINS\<Name>\`, runnable as `./build.sh <drive|none>` from that folder;
- `source "../shared/usb_stick.sh"; pick_drive "$@"` near the top (build-all finds plugins by the word `pick_drive`)
  and `copy_to_stick "$ZIP" "<zip prefix>" || exit 1` as the last step; exit non-zero on any failure;
- no other `read` prompts (stdin is /dev/null under build-all), and print the zip path `dist/<Name>-X.Y.Z-mpc-aarch64.zip`
  (release.py does) so the summary can show it;
- `vst/vst.json` with `"version"` (the menu shows it). A folder with a build.sh that should not be built: add
  `.no-build-all`.

Expected build output that is **not** a problem:
- `warning: knob r=… filmstrip is over MPC's 16384 px image limit`: handled by `skin_post.py` (section 5).
- `warning: skin: … TOUCH … overlap by ~10 px` when knobs are drawn touching: only the transparent margins overlap.
- `vst2_wrap.c: 'render_frames' defined but not used`: a warning inside the toolchain itself.
- `warning: skin: … TOUCH  and  overlap by <cell size>` once per preset (plugins with the on-screen preset browser):
  each browser cell has a highlighted copy on the same spot (`when=pre_hl:<n>`), by design.

## 4. Skin geometry

- The plugin area is **1280 x 628**. `layout.conf` y = screen y **+ 86** (Force Shadow coordinates, `Y_OFF`).
- Scale a 1920x1080 mockup **uniformly** by 628/1080 (= 1116 x 628) and left-align it. Never stretch it to
  1280x800, and don't squash it. Keep watched controls left of x ≈ 1025: MPC's Q-Link sidebar covers the right
  edge while a Q-Link is held.
- **Knobs and text big enough to read on the MPC Live III's small screen** (user's standing request, 2026-11-06):
  knobs r ≥ 32 in tight rows, r ≥ 55-60 in panels and main grids; value text ≥ 24 px (≥ 30 in r 60 knobs), labels
  ≥ 24 px. PoliPlug 1.4.0's r 34 sidechain knobs and r 26 row knobs, and Poli-q's first r 26 Dynamics knobs, were too
  small. Give a panel the room (a one-row knob strip across most of the screen) rather than shrinking the knobs.
- Bake every static part (title, labels, frames, panels) into one background: `art file=skin_assets/bg.png fit=stretch`.
  Only live controls are widgets. Take the drawn controls out of the mockup by pasting the clean background over
  them (a mask slightly bigger than each control), at full resolution, before scaling.
- When a widget sits in a hole of the background, fill the hole in the background with the surrounding colour,
  a few px wider than the hole. A white hole leaves a light halo after scaling and JPEG edges.
- Let `generate_skin.py` write `layout.conf` from the same constants it draws with, so art and touch areas can't drift.
- Labels baked into the art: give knobs `label="" ns=0 vs=0` (no MPC name or value text).
- New labels that the mockup doesn't have: render ALL labels in one font fitted to the mockup's lettering (overlap
  score against a crop over weight, size and tracking). Poli-Ess's Canva labels = Open Sans 650, 51 px (mockup), +1 px
  tracking; the font (SIL OFL) lives in `imgs/fonts`.
- Preview before every device build: `tools/studio.py preview "<skin>/Plugin Skins" -o page_%d.png`. It draws every
  control at one fixed position (frame 40 of 128), so composite your own defaults/at-rest picture for comparisons.

## 5. Filmstrips and MPC's limits

| Rule | Detail |
|---|---|
| **numFrames = exact frame count** (**device**, Live III 3.10) | MPC takes one frame's height as `image height / numFrames`. The builder's own "one fewer for rotary knobs" convention (128 frames, numFrames 127) makes each frame a few px too tall: knobs slide up/down into the next frame, worse the further they turn |
| Image height ≤ 16384 px | Taller images draw wrongly. The builder always makes **128-frame** knob strips (frame = 2r+10 px), so any r > 59 needs `skin_post.py` |
| Meter / slider strips ≤ 12288 px | Builder limit (`MAX_STRIP`). Their frames are exactly the widget's w x h |
| Odd knob frame count | One frame sits exactly at the middle (pointer straight up at 50 %) |
| Knob box | The builder draws a knob into a (2r+8) box centred in a (2r+10) frame with a transparent 1 px margin |

`skin_post.py` (runs after the skin is built: `python3 skin_post.py "<skin dir>"`): for every `sh_knob_*` FilmStrip
taller than 12288 px, replace the PNG with your own `skin_assets/knob_strip.png` (N frames of 2r+8, pasted at a 1 px
offset into 2r+10 frames), or resample to as many frames as fit, and set `"numFrames": N` in `TUI.json`.
Example: r = 90 gives 63 frames x 190 px = 11970 px.

## 6. Engine contract and live values

- `mpc_engine()` returns create/destroy/midi/set_param/get_param/render/process. Audio is 44.1 kHz int16
  interleaved stereo in 128-frame blocks (2.9 ms per block for everything on the track). Effects implement `process`
  and set `"effect": true`. Chunk any loop over `frames` into 128-frame pieces anyway.
- `set_param` receives numbers as strings in the parameter's own units; an option list arrives as its index (`"0"`, `"1"`).
  `get_param` returns the same form (an option as its index).
- **`get_param` must return full precision** (`"%.4f"`, never `"%.0f"`). The wrapper reads the knob position back from
  this text, and MPC nudges Q-Links and the data wheel from what it read back. MPC rounds the value it *shows* itself
  (whole numbers when the range is over 20). With a rounded read-back, Poli-Ess 1.0.3 ran Q-Link turns 28 % fast on
  Intensity and left fine moves stuck (offline, through the real wrapper).
- **Validate in `set_param`**: parse with `strtod`, ignore non-numbers and non-finite values, clamp to the range.
- **Glide every parameter the audio depends on** (~10 ms one-pole per sample; filter re-tunes every 16 samples), and
  crossfade switches (~10 ms). Hard steps click on every Q-Link event: Poli-Ess 1.0.3 measured 17x the clean 3rd
  difference on Freq moves and a 6x step when Diff switched over a low tone.
- **Flush tiny filter states to zero once per block** (`|z| < 1e-15`). `-ffast-math` does not set flush-to-zero for
  a shared library, and the subnormal tail after loud audio ran 5.8x slower on x86.
- **A value the engine changes itself** (a gain-reduction meter): mark the param `"live": true`, define
  `HAS_DISPLAY_REV` and `DISPLAY_REV_NO_UPDATE`, and answer `get_param("display_rev")` with a counter you bump only
  when the shown value changes. Quantise to the meter strip's frame count so you don't bump it every block. The wrapper
  polls every 100 ms and reports the moved values; `DISPLAY_REV_NO_UPDATE` avoids rebuilding the whole screen 10x a
  second. The meter widget: `meter cx= cy= w= h= key=<param> strip=… frames=N` (frame 0 = minimum).

## 7. Parameters: gotchas

- **Two-state switch (toggle) on a Q-Link shows inverted** (**device**). MPC sends `last value ± 1/128`; the wrapper
  turns that nudge into the next option, but MPC keeps and draws the value it sent (0.008 means "off" on screen while
  the engine is on). Fix on the param: `"refresh_display": true` (MPC re-reads after each write) plus
  `"qlink_ticks": 4` (4 Q-Link events in one direction per flip, so a brush of the knob doesn't toggle it; the data
  wheel then needs 4 clicks too). Checked with a mock host (`mpc_sim.c` beside this doc): 10/20 inverted before,
  0/20 after.
- Drawing a switch as a knob: a `toggle … w= h= img=off.png img_on=on.png ns=0` with two knob pictures (pointer at
  min / max). These are separate images, so they are not subject to the filmstrip rules.
- Whole-number parameters: `"display": "int"`. Text readouts: `"display": "string"`.
- Anything slow in `set_param` (file loads) must be a button or stepper, never a knob (a drag fires many calls).
- Never reorder `params.json`; append. Changing a parameter's type at the same position (a 0..1 knob into an
  Off/On option list) is fine.
- **Log-scaled knobs** (times, frequencies over decades): params are linear, so store the knob *position* (0..100),
  convert in the engine (`lo * (hi/lo)^(pos/100)`), and set `"dynamic_display": true` so MPC shows the real value from
  `get_param("<key>_display")` ("0.80 ms"). Preset values are then positions too: convert in a small script.
- `"cflags"`: add `-U__FAST_MATH__` next to `-ffast-math`. Per-sample `log10f`/`powf`/`sinf` loops otherwise get
  vectorised into libmvec calls under newer glibc headers (`NEEDED libmvec.so.1`; seen with Shhhhh). Check
  `readelf -d` on every new `.so`.

- **Never let a knob's value show up in a text readout** (`"display": "string"`, e.g. a status line). The wrapper polls
  those texts and sends an UpdateDisplay when one changes; MPC rebuilds its screen on each, which drops a touch drag in
  progress, so the knob "sometimes doesn't respond" (PoliPlug 1.3.1's Send knob with "Send 40 %" in the status,
  2026-11-05; offline test: 6 UpdateDisplays in a 0.5 s drag). The knob shows its own value (`dynamic_display`).
- Controls at x >= ~1025 are covered by MPC's Q-Link sidebar for a moment after a Q-Link is touched.

## 7b. Presets (MPC's PRESET menu)

- Simplest: `vst.json "presets": "presets.json"` = `{"presets": [{"name": "...", "values": {key: value}}]}` (names
  <= 24 chars, values in param units or option labels). The wrapper sets each value and reports it to MPC; nothing in
  the engine. Extra keys (`"about"`) are ignored. Write the file from a script that holds the sources.
- **Picking the preset that is already current is ignored** (MPC's JUCE host re-selects it at project load; the guard
  keeps saved edits). A fresh insert counts as preset 0, so make preset 0 "Init" = the params' defaults. To return to
  an edited preset, pick another one first.
- Every value a preset changes glides in the engine (section 6), so switching presets mid-audio doesn't click.
- `test_port.sh` checks names, picking and the host report; Poli-Ess `test/host_sim.c` adds Init = defaults, Diff
  reset, MPC in sync and a no-click switch during audio.

## 7c. On-screen preset selector (Poli plugins, 2026-11-05)

- Shared code in `C:\MPC-PLUGINS\shared\`: `preset_nav.h` (engine side, copied into each plugin's `src/` by its
  generator, because the Docker build mounts only the plugin folder) and `poli_preset_ui.py` (draws the selector and
  browser in the plugin's own colours and font, appends the parameters, returns the layout lines). Used by Poli-Ess,
  Poli-Multiband and Shhhhh; not Poliwow (its own arrows, kept as is).
- Parameters (appended): `preset` (option list, also `"programs": {"param": "preset"}`), `preset_prev`, `preset_next`,
  `preset_list` (momentary), `browsing` (Off/On, engine-owned), `pre_hl` ("-", 1..N: the highlighted cell), `pick1..N`.
  The engine applies presets itself and reports the moved keys through `mpc_engine_changed`.
- Skin: the name is a `picture` (one PNG per preset, the plugin's own font), a transparent `button` over it opens the
  browser, arrows are `button`s; the browser is a backdrop `button` (same key: a tap on it closes) and one `button` per
  cell, `when=browsing:On`, plus a highlighted copy `when=pre_hl:<n>`. All of these bake nothing, so `when=` is safe.
  They come after every other control in layout.conf, so the browser is on top.
- A pick from the browser reloads even the current preset (brings back an edited one); a host write of `preset` (the
  PRESET menu, JUCE's re-select at load) is ignored when it is already current. Keep the preset index in the engine's
  `state` and only *name* it on restore, or a restore re-applies the preset over the saved values.
- Momentary buttons: the wrapper ignores a second press within 250 ms (`debounce_ms`), so tests that tap the same
  button twice must wait ~260 ms.
- PoliPlug looks for a hosted parameter named exactly **"Preset <"** to know an effect draws its own selector.

## 7d. Programs that change at run time (`PROG_DYNAMIC`, wrapper change 2026-11-05)

- `vst.json "defines": {"PROG_DYNAMIC": 1}` with `"programs": {"param": "<key>"}` on a whole-number param: the program
  count is the engine's answer to `get_param("<key>_count")` (1..NPROGRAMS), names come from `"<key>:<n>"` as before.
  `vst2_wrap.c` sets `numPrograms` from it at creation and before every `audioMasterUpdateDisplay` (MPC re-lists the
  programs on each one). Plugins without the define are unchanged. Used by PoliPlug (`hpreset`, max 128): the opened
  effect's presets in MPC's PRESET menu. **Not yet checked on a device** that MPC re-reads `numPrograms` there.
- Such a parameter is on no screen: mark it `"legacy": true` so `test_port.sh` doesn't step it like a knob (it can't move
  while there is nothing to pick).

## 8. Q-Links

`qlinks "PAGE" = key1,key2,...` per tab: keys 1-8 are bank 1, 9-16 bank 2. In the built Q-Links.json the first four
keys land on Q-Links 13, 9, 5, 1 and the next four on 14, 10, 6, 2 (the grid is numbered bottom-up), so a 4x2 knob grid
in reading order = Q-Links 1-4 top row, 5-8 bottom row. Keep one bank of ≤ 16 per tab
(a second bank shows MPC's sub-page arrows). Nothing destructive on a Q-Link. Display-only widgets (meters) are not
Q-Linked.

**Live III Q-Link pages (device, 2026-11-06):** the Live III has 4 Q-Link knobs and shows the 16 Q-Links as 4 pages:
page 1 = Q-Links 13, 9, 5, 1 top to bottom, page 2 = 14, 10, 6, 2, page 3 = 15, 11, 7, 3, page 4 = 16, 12, 8, 4. That is
the `qlinks` key order in groups of 4: key 1-4 = page 1 (top first), 5-8 = page 2. Users count "page p, knob k", so plan
Q-Link assignments as pages of 4 (the user's PoliPlug rules: a Parallel rack page of 4 Sends = one Q-Link page; a
sidechain panel = Threshold, Attack, Release, Knee on page 1, Ratio top of page 2). An engine that answers Q-Links by
number (proxies) must convert: slot = (n%4)*4 + 3 - n/4 for Q-Link n+1 (PoliPlug `q_slot`).

Hosts (PoliPlug): the Q-Links follow **what is on screen**. A page's Q-Links must not stay on something that was
opened before (PoliPlug 1.4.0 left them on the last opened effect while back on the rack, which turned it by
surprise). With no page of its own on screen, map them to that screen's own knobs (PoliPlug's Parallel Sends, a
panel's knobs) or to nothing ("-").

## 9. Testing ladder

1. `test_port.sh` (x86, sanitizers): must PASS.
2. A DSP test that links the engine directly (template: `Poli-ess/test/dsp_test.cpp`): response, the effect's job,
   silence in = silence out, full scale doesn't wrap, garbage values, **clicks** (3rd difference of the output while a
   parameter moves in Q-Link steps; parameter changes land between 128-frame blocks), denormal timing, CPU.
3. A mock MPC host linked against the real `vst2_wrap.c` (template: `Poli-ess/test/host_sim.c`): MPC keeps the value it
   sent and re-reads only on Automate / UpdateDisplay. Test that Q-Link (1/128) and fine (1/1000) moves land where MPC
   sent them, toggles catch up on screen (the wrapper sends at most one UpdateDisplay per 50 ms; requests wait, never
   dropped), meters reach MPC, and save + reload restores everything. `run_tests.sh` builds both under ASan/UBSan, and
   `build.sh` runs it after `test_port.sh`.
   Check that every new test **fails on the old code** before trusting it passes on the new.
4. Preview PNGs and a side-by-side against the mockup.
5. On the device: insert on a track, turn every knob min to max (frames stay whole and centred), Q-Link every
   control, check the meter moves, save and reload the project.
Only call something "verified" after step 5, and say which device and OS version.
